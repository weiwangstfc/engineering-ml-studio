# Phase 1 implementation plan — landing page + Explore mode prototype

> **Prototype scope.** This plan covers the **first** Phase 1 increment only: a new landing page, a
> clear front door into a new beginner **Explore** mode and into the existing **Project** mode, and
> **one** guided Explore workflow built on existing datasets and existing regression functions. It
> is **not** a full application redesign.

> **Revision (problem-led engineering Explore).** After the first increment was reviewed, Explore mode
> was revised to be **problem-led and engineering-focused**. The generic, example-picking flow
> described in §2–§3 below has been superseded: Explore now opens on a concrete mechanical/thermal
> problem — **predicting pressure drop in a pipe** — and its four stages became *understand the
> problem → choose an approach → train and compare predictions → interpret the engineering meaning*.
> Stage 2 presents plain-language **approaches** (simple trend = Linear, more flexible = Random Forest,
> compare = all three) with model names shown only as secondary detail; results are reported in
> physical units (kPa) and Stage 4 adds an engineering-trend and extrapolation check. A new synthetic,
> documented dataset (`examples/pipe_pressure_drop_sample.csv`, from the **Darcy–Weisbach** equation,
> generated by `scripts/generate_pipe_pressure_drop.py`) is the primary example — a **training
> demonstration, not a design tool**. The inherited nonlinear example is kept as a labelled secondary
> maths demonstration; the house-price example was removed from Explore only (its CSV is retained).
> **This revision did not change the router (`js/modes.js`), Project mode, the ML engine, licences, or
> deployment.** The architecture, reuse, and non-goals in §1 and §4–§7 still hold; see
> [`EXPLORE_MODE.md`](EXPLORE_MODE.md) and [`../examples/README.md`](../examples/README.md) for the
> current, authoritative description of the delivered flow.

## 1. Confirmed current implementation (from inspection)

### Entry, shell, and script loading

- **Entry page:** `index.html` (522 lines). A single static page: a top `<header class="app-header">`
  (brand/title "Local Regression Studio", language selector, `#runtimeMode` status pill) followed by
  `<main class="app-shell">` containing the whole Project workflow, then several `<dialog>` elements.
- **No inline scripts** are allowed: the page's CSP is
  `script-src 'self' https://cdn.jsdelivr.net` (no `'unsafe-inline'`). All new JS must live in
  external files under `js/`. `connect-src 'self'` permits `fetch('./examples/*.csv')`.
- **Script loading:** `index.html` loads `js/build-config.js`, `js/i18n.js`, then `js/bootstrap.js`.
  `bootstrap.js` sequentially injects every module (`ml-core`, `advanced-core`, `modelling-core`,
  `platform-core`, `worker-client`, `comparison-core`, `security-core`, `governance-core`,
  `recovery-core`, `validation-core`, `approval-core`, `app.js`) and each exposes a global
  (`window.MLCore`, `window.LRSPlatform`, …). `js/app.js` calls `init()` on load and assigns
  `window.LocalRegressionApp` — our readiness signal.

### The eight-stage workflow and how sections show/hide

- Stages are `<section class="panel" id="step-upload|features|preprocess|model|split|diagnostics|predict|monitor">`
  inside `<section class="workspace">`, with an `<aside class="sidebar">` step list.
- Downstream panels start with class `locked` (`.panel.locked{opacity:.52;pointer-events:none}`).
  `unlockPanel(id)` removes `locked`; `unlockWorkflow()` unlocks panels as prerequisites are met.
  `.hidden{display:none!important}` toggles visibility of sub-elements.

### State

- All Project state lives in a single `state` object inside the `app.js` IIFE (rows, headers,
  profiles, target, selectedFeatures, artifact, experiments, plotMap, …). It is **not** exported;
  only a small API is exposed on `window.LocalRegressionApp`. Explore will keep its **own** small
  state object and will **not** reach into Project state.

### Reusable functions (the key finding — no ML duplication needed)

CSV parsing, column inference, splitting, preprocessing, training, prediction, and metrics are all
available as **globals** and are exactly what Project mode itself uses:

- `window.CSVEngine.parse(text, {header:true, skipEmptyLines:true})` → `{data, errors, meta:{fields}}`.
- `MLCore.inferColumns(rows, headers)` → per-column `profiles` (type numeric/categorical, etc.).
- `MLCore.autoSelectFeatures(headers, target, profiles)` → default feature list.
- `MLCore.splitRows(rows, target, {seed, percentages})` → `{training, validation, test}` (each an
  array of `{row, index}`); deterministic for a fixed seed.
- `MLCore.fitPreprocessor(trainRows, features, config, profiles)` and
  `MLCore.transformRows(rows, preprocessor, target, requireTarget)` → `{X, y, rowIndices, …}`.
- `MLCore.fitTargetTransform` / `applyTargetTransform` / `inverseTargetTransform` / `fitSmearing`
  (Explore uses target transform `'none'` for simplicity).
- `LRSPlatform.getModelAdapter(type)` → `{fit(X,y,params,seed), predict(model,X), …}`. The adapter
  is a thin wrapper over `MLCore.trainModel`/`predict`. Native model types include **`linear`**,
  **`tree`**, **`forest`** (plus ridge and, via `modelling-core`, gboost/knn/quantile).
- `MLCore.metrics(actual, predicted)` → `{r2, rmse, mae, mse, n}`.
- `window.Plotly` (bundled `vendor/plotly-3.3.1.min.js`) for the actual-vs-predicted scatter.

**Safe default parameters (from the current Project UI):**
- Linear: `{}` (no hyperparameters).
- Decision tree: `{maxDepth:8, minLeaf:5, maxThresholds:24, maxFeatures:'all'}`.
- Random forest: `{nTrees:40, maxDepth:8, minLeaf:5, sampleRate:0.8, maxThresholds:20, maxFeatures:'sqrt', maxRowsPerTree:20000}`.

**Reusable preprocessing config** (validated by the baseline unit test):
`{numericScaling:'standard', numericMissing:'mean', categoricalEncoding:'onehot', categoricalMissing:'mode', dropFirstCategory:false, maxCategories:50}`.

### Tightly coupled parts (deliberately avoided)

- `app.js` `trainAndEvaluate()` (~175 lines) is tightly bound to the Project DOM (reads dozens of
  `#id` controls, builds governance/approval/experiment artifacts, renders six-plus Plotly charts,
  optionally offloads to a Web Worker). Reusing it directly from Explore would drag in the whole
  Project UI. **Explore will not call `trainAndEvaluate`.** Instead it re-creates the *same
  computation* by calling the shared `MLCore`/`LRSPlatform` functions above — this reuses all ML
  math with **zero duplication of numerical code**, only a short orchestration function.

## 2. Proposed information architecture

A thin **view/router layer** over the existing page. Nothing is removed.

```
┌ global top nav (always visible): brand "Engineering ML Studio" · Home · Explore · Project · About
│
├ #view-home     — landing/hero: product statement, safety + privacy notice,
│                   two primary routes (Explore with an example / Build a project),
│                   secondary: "Learn with Python (Coming later)", "Open saved work" (progressive disclosure)
│
├ #view-explore  — beginner four-stage workflow (new): Choose example → Select model →
│                   Train & compare → Understand results; own stage indicator + back/next
│
├ #view-project  — the EXISTING app (unchanged internally): the current app-header + app-shell
│
└ #view-about    — short about: purpose, local-only, not safety-critical, attribution to Yu Duan
```

- Only one view is visible at a time (`.view.is-hidden{display:none}`). Home is the default view so
  there is no flash of Project mode during async bootstrap.
- The existing `<header class="app-header">` and its `<h1>Local Regression Studio</h1>` are retained
  **inside `#view-project`**, so Project mode is visually and behaviourally unchanged.
- "Open saved work" in the landing page simply routes to Project mode (Step 1 already hosts
  Open project / Load model / Load approved package). No loading logic is duplicated.

## 3. Proposed state transitions

**Router (`js/modes.js`)** — a tiny finite state machine:

```
show(view):  hide all .view → show #view-<view> → mark nav active → set document focus to the view heading
             → update location.hash (#home|#explore|#project|#about) for back-button support
init():      read location.hash (default 'home') → show(view)
```

**Explore controller (`js/explore.js`)** — its own state and a linear stage machine:

```
exploreState = { exampleKey, modelType, params:{maxDepth,nTrees}, dataset:{rows,headers,profiles,target,features},
                 results: { [modelType]: {train, test, actual, predicted} } }

Stage 1 Choose example  → on select: fetch+parse CSV once, cache dataset, enable "Next"
Stage 2 Select model    → pick linear|tree|forest; show 1–2 educational controls; safe defaults
Stage 3 Train & compare → "Train this model" and "Train all three": run shared pipeline on main
                          thread, store metrics + predictions, draw actual-vs-predicted, small
                          comparison table (test RMSE, test R²)
Stage 4 Understand      → deterministic, rule-based interpretation of the selected model's numbers
```

Explore never mutates Project `state`; switching to Project mode leaves the inherited app intact.

## 5. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Wrapping the app-shell breaks `app.js` init (missing `#id`s) | No Project element is removed or renamed; only a wrapper `<div>` is added. `app.js` `init()` binds by id and still finds everything. |
| Flash of Project mode before router runs | Home is the default-visible view via CSS; other views ship with `is-hidden`. |
| Plotly renders zero-size in a hidden view | Explore plots are drawn only while Explore is visible (user-triggered); `Plotly.react` + `responsive:true`, re-layout on view show if needed. |
| Existing smoke tests fail on new entry path | Add `enterProjectMode()` and document each change; keep all original assertions. |
| Duplicating ML logic | Avoided — Explore calls the same `MLCore`/`LRSPlatform` functions Project uses; only orchestration is new. |
| Random forest slow on main thread | Datasets are ≤400 rows and defaults are modest (40 trees); acceptable. Worker offload is a future option. |
| CSP blocks new code | All new JS is external (`js/*.js`, `'self'`); no inline scripts or new origins. |

## 6. Testing strategy

- **Keep all 17 baseline tests green.** `unit.spec.js` is unaffected (it only evaluates `MLCore`
  globals). `smoke.spec.js` gains an `enterProjectMode()` step; every original assertion is retained.
- **New `tests/explore.spec.js`** covers the 14 required scenarios: landing loads; Explore/Project
  choices visible; entering Project reveals the workflow; return home; Explore shows four stages;
  select example; train Linear; metrics appear; actual-vs-predicted appears; interpretation text
  appears; switching models does not crash; no non-local requests under `?localOnly=1`; keyboard can
  reach primary actions; narrow viewport (e.g. 390 px) has no horizontal overflow.
- All tests run under `?localOnly=1` and assert **no non-local network requests**.

## 7. Explicit non-goals (this increment)

- No frontend framework, bundler, server, database, accounts, cloud/AI APIs, or Plotly replacement.
- No new ML algorithms; no change to existing ML calculations.
- No refactor of `app.js` or the Project-mode layout; no removal of preprocessing, diagnostics,
  export, prediction, monitoring, or governance features.
- No real notebook/Python integration (the "Learn with Python" route is labelled *Coming later*).
- No new datasets; no recreation of `editions/` or launcher scripts.
- No deployment or GitHub Pages changes; no full WCAG audit (sound accessible practice only).
